# 阶段一设计：社区贡献与平台治理

## 目标与范围

对应[路线图](roadmap.md)的阶段一，覆盖 P0-3 与 P0-6。拆成 **1.1 基础贡献审核、1.2 完整贡献类型、1.3 举报与治理** 三次完整交付。
每次都有用户页面、后台页面、接口和验证，避免只有基础设施没有可用流程。

本文从 `96ef1d5` 的资源基础出发；1.1 已实现并验收，1.2、1.3 仍为待实施设计。
不在本阶段做搜索、收藏、交换、认领、讨论、通知系统或通用工作流引擎。
用户通过本人贡献/举报页面查看结果，不以新增邮件队列或通知平台作为前置。

## 现有能力如何复用

| 已有能力 | 本阶段用法与边界 |
| --- | --- |
| 账号、验证、会话与 CSRF | 公共端沿用现有认证；提交要求有效账号及已验证邮箱，不新增认证体系 |
| Admin 静态角色 | Editor/Admin 审核普通知识变更；Moderator 的内容只读边界保留，处理举报不等于获得资源编辑权 |
| curation 应用层 | 复用规范化、资源版本检查、来源/分类/关系不变量；接受提议与正式变更必须处于同一事务 |
| 公开读取与资源页面 | 提议不能直接进入公开资源；正式资源继续使用现有可见性与隐私规则 |
| Goose/sqlc 与数据库角色 | 新能力追加迁移和最小对象权限；不改写 00001～00006，不修改集群角色或共享基础设施 |

`curation.App` 的常规写方法各自开启并提交事务。1.1 已增加受控的 `ApplyReviewedTx` 协作入口，
将「检查审核权限 → 锁定提议/正式资源 → 应用变更 → 记录结果与审计」原子完成。
不能先调用一个已提交的 curation 方法，再用另一个事务把提议标为已接受。
保留事务内会话/角色重验、锁顺序、CAS 和真正无变化时不增加版本的行为，不重写 Auth。

## 1.1 基础贡献审核

**交付目标：一条从普通用户提议到审核入库的真实流程。**

首批支持新资源提议和已有公开资源的基础资料修改，包含名称、摘要、描述等普通知识字段。
新资源表单携带默认语言、分类及必要的来源信息，允许说明为何暂时没有来源。
对已有资源新增或移除来源、标签、关系、多语言翻译在 1.2 一次补齐。

公共端提供提交/建议编辑入口、本人贡献列表、详情和撤回；后台提供队列、当前值与提议值对比、接受和拒绝。
用户已确认允许审核者修订后接受，必须保留用户原稿、最终采纳内容及修订原因；不能静默改写原稿或借此绕过版本冲突。
提交时做输入规范化、长度限制、重复请求保护以及基础提交频率/待审数量限制。
首版是显式人工审核，不依据基础信任状态自动接受，不自动合并相似资源。

### 提议与审核规则

- 状态为待审核、已接受、已拒绝、已撤回。提交内容及其基准保存为不可静默改写的记录；需要修订时撤回后新建并关联原提议。
- 已有资源提议记录提交基准和变更字段。审核时比较当前资源，旧版本不能自动重试或覆盖；冲突时保留待审核状态，明确要求重新提交或拒绝。
- 新资源接受后创建正式草稿，由现有 curation 发布流程决定公开；已有资源的接受变更保持原发布状态。接受不等于自动发布或推荐。
- 作者可以撤回尚未处理的提议，不能替他人操作。审核者不审核自己的提议；管理员直接编辑仍可使用既有 curation。
- 只允许一个终态成功。接受、拒绝、撤回及重复请求并发时，不得重复创建资源、重复增加版本或出现一半成功。
- 历史分开记录贡献过程与必要业务审计，不写入 Auth 安全事件，不保存任意敏感请求原文。

### 权限与隐私

作者仅查看自己的提议及安全的处理结果，授权审核人员可查看队列；P0 不开放他人待审内容或内部审核备注。
普通修改的接受/拒绝要求 Editorial；提交者不能通过提议设置发布状态、版权状态、限制状态或软删除。
角色撤销、会话失效和资源可见性变化必须在实际处理时重验。
若资源后来变为隐藏/删除，作者仍可看到安全的处理状态，但不得据此读取当前隐藏资源、关系对端或内部治理数据。

### 完成验收

普通用户提交 → 后台看到差异 → 接受 → 创建草稿/更新原资源 → 既有发布流程 → 公开页面可见，整条流程可从 UI 完成。
拒绝和撤回不改变资源；未验证账号、越权读取、自审、旧版本、重复接受、撤回竞争、角色撤销和中途失败均有针对性验证。
基本额度从本次起生效，不等 1.3 才保护提交入口。

## 1.2 完整贡献类型

**依赖：1.1。交付目标：总纲规定的 P0 贡献类型全部可用。**

| 提议类型 | 表单与审核重点 | 正式入库约束 |
| --- | --- | --- |
| 新增来源 | URL、类型、说明和来源依据 | 复用 URL 规范化/去重；不允许贡献者自授版权确认 |
| 移除失效来源 | 指定来源和原因 | 更新 availability，不硬删除；保留来源与处理历史 |
| 添加标签 | 选择现有有效标签并说明 | 拒绝新增退休/删除标签绑定，不顺带开放用户维护 taxonomy |
| 添加关系 | 公开对端、关系类型及理由 | 复用固定图锁、两端顺序锁、按类型环检查与双端版本更新 |
| 添加/修订翻译 | 语言、名称、摘要和描述差异 | 保持默认翻译完整、长度限制和语言回退，不顺带改变默认语言 |

共用 1.1 的提议生命周期、本人历史、后台队列、拒绝理由和原子接受机制，不为每种类型建立独立审核系统。
关系提议展示并校验相关两端的基准；对端变为不可见、版本变化或出现环时明确冲突，不泄漏隐藏信息。
普通用户不提交版权裁定或更改 taxonomy 生命周期，这些继续使用既有后台权限操作。
本阶段不增加软删除资源恢复功能。

**完成验收：** 每种类型均可从表单提交并从后台处理；来源去重/保留、退休标签、翻译缺失、关系环与并发变更均得到正确处理。
失败完整回滚；公开 API、SSR、Resource CAS 和 1.1 流程回归通过。

## 1.3 举报与治理

**依赖：1.1、1.2。交付目标：平台能持续处理争议、滥用与失效内容。**

公共端增加资源/来源举报、本人举报状态；后台提供问题队列、处理记录、限制管理、信任与额度管理、审计查询和来源健康入口。
举报的受理、解决、驳回与资源修改是不同动作，不能以“举报数量多”自动下架，也不能把举报变成公开评论。
举报正文、举报人身份和内部处理备注不向公众或被举报者公开；本人只收到可公开给自己的状态与结果摘要。

| 能力 | 首版规则 |
| --- | --- |
| 角色职责 | Moderator/Admin 受理和处理举报；Editor/Admin 做普通知识修正；版权、restricted/removed、软删除及账号范围限制由 Admin 决定。没有相应能力时转交，不借举报接口越权 |
| 范围限制 | 针对已实现的提交等行为设置原因、有效期和撤销记录；应用层在写事务内检查，限制与提交并发时结果一致，不仅禁用前端按钮 |
| 基础信任与额度 | 保留 New/Established/Trusted 内部状态，首版由 Admin 维护并留痕；影响明确的额度策略，不赋予 Admin 角色、不绕过审核、不公开万能分数 |
| 内容资格 | 分清可收录、可展示来源与可推荐；治理策略由后续搜索/发现复用，不另造一套矛盾的可见性规则 |
| 业务审计 | 高影响治理及正式知识变更记录操作者、对象、动作、必要差异/原因和时间；与实际变更一致提交，限制查询权限，不滥存隐私或秘密 |
| 来源健康 | 展示异常来源与处理状态，记录核查结论/时间并修正 availability；首版通过举报和人工核查闭环，不自动请求任意 URL 或引入爬虫/巡检队列 |

固定额度和有效期等具体数值在相关子阶段实施规格中统一确定；不用可编程策略引擎或动态 RBAC 解决首版问题。
内部信任与业务限制归治理领域，不改造已验收的账号认证系统；需要 Auth 协作时保持窄边界。

**完成验收：** 举报受理 → 核查 → 有权者执行修正/限制 → 记录处理结果 → 作者查看安全状态，整条链路可操作。
限制撤销/过期与并发提交、Moderator/Editor/Admin 权限差异、审计原子性和举报隐私均验证通过。
来源异常能从发现进入处理并反馈到资源页面；阶段二可以直接消费确定的内容资格规则。

## 数据与实现边界

提议公共字段、类型化变更、处理历史、举报、治理动作、限制与信任数据按实际子阶段建立关系模型。
不使用 JSONB/EAV 保存万能提议、不建通用流程引擎；不要一次预建全部后续领域表。
业务额度的权威状态在 PostgreSQL，Redis 只可承担可丢失的节流，不得因缓存清空绕过业务规则。

Public API 对正式 Resource Core 继续只读，仅新增所需的提议/本人记录等最小权限；
Admin 获得审核治理新表的必要权限，正式资源写入继续沿用既有权限边界；Worker 不因本阶段自动获得 Resource 权限。
具体表/列授权随迁移和集成测试明确，readonly 只读，集群角色不变。
新功能需要从版本 6 之后追加 Goose 迁移，不能继续套用 P0-2C“版本始终为 6”的历史阶段限制；00001～00006 内容不变，共享开发仍只做 up。

不新增来源自动抓取、全文检索引擎、通知系统、附件上传、后台角色分配或未来领域空包。
API 合约仍先定义再生成；贡献表单复用现有前端边界，不给匿名 Resource SSR 页面增加个人数据或凭据转发。
