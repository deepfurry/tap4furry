## 交付目标

一次完成两种提议及其前后台流程：**提交新资源、修改已有资源基础资料**。

```text
已验证用户提交 → 本人查看/撤回 → Editor/Admin 查看差异
    → 原样接受或修订后接受 → 原子入库 → 既有发布流程
    → 拒绝并说明原因
```

用户提交的是知识变更建议，不直接修改正式资源。
新资源接受后形成草稿；已有资源接受后保持原发布状态，已发布资源的修改可以随正式读取呈现。
审核接受不自动发布、不自动进入推荐。Moderator 不获得接受/拒绝权限，角色分配仍只有 owner 的 `adminctl`。

不实现 1.2 的独立来源/标签/关系/翻译提议，也不实现举报、信任等级管理、搜索、集合、通知、附件或通用审核引擎。
新资源随附最多一个初始来源是创建表单的一部分，不因此开放已有资源来源维护。

## 用户提交什么

### 新资源

| 字段 | 首版规则 |
| --- | --- |
| 名称 | 必填，1～160 个 Unicode 字符 |
| 简介 | 可选，最多 500 字符；没有来源时必须填写，避免空记录 |
| 说明 | 可选，最多 50,000 字符，普通 Markdown textarea |
| 资料语言 | 必填，表示本次名称/简介/说明的默认语言，不是作品支持的语言；沿用现有 locale 规范化 |
| 分类 | 必填，选择现有有效分类；不能在提交过程中创建分类 |
| 生命周期 | 可选，默认 unknown，使用已有状态 |
| 内容分级 | 必选，沿用 general/mature/explicit，不以默认普通级别代替用户判断 |
| 初始来源 | 最多一个 HTTP(S) URL，可带类型和简短标签；类型可为 unknown；不上传文件、不抓取远端内容 |
| 提交理由 | 必填，1～2,000 字符，说明资源与平台的关联；无来源时同时说明原因 |

用户不必填写技术性的 slug。审核者接受前设置合法且唯一的 ASCII slug，沿用现有规范；不加入音译库。
来源 rights_status 固定从 unknown 开始；初始 availability 由审核者确认，唯一初始来源作为 primary。
填写“官方来源”不等于版权已确认、链接安全或已经由系统探测。

### 修改已有资源

只允许对**当前公开资源**提出修改，且本阶段只修改默认语言资料：名称、简介、说明，以及分类、生命周期和内容分级。
未提供的字段保持原值；简介/说明显式清空表示置空。规范化后至少有一处实际变化，不能提交无变化的提议消耗队列。

slug、默认语言切换、发布状态、版权、删除/恢复、外部 ID、来源、标签、关系及其他语言不在本次修改范围。
新增翻译放到 1.2；提议页面明确显示正在编辑的默认语言，不能将浏览页的语言回退结果误当成该语言原文。
修改理由必填，最多 2,000 字符；可选关联一条本人旧提议，便于修订后重新提交，不自动继承其状态或审核结果。

## 提交基准与冲突

进入编辑表单时，独立的登录态接口返回当前可编辑资料及**不透明基准标识**，不修改现有匿名 Resource DTO，不暴露其内部 version。
标识绑定当前用户、目标资源和服务端版本，不能靠客户端传任意版本伪造；请求始终重验认证、归属和资源可见性。
不将该标识当成登录凭据或 CSRF 凭据，也不记录进访问日志。

提交时用一致快照验证标识并保存服务端读取的基准及内部版本。原稿与基准分开保存，不能相信客户端提交的“原值”。
不为此给 Public API 增加 Resource UPDATE 或锁定权限。提交之后发生的正式修改由审核事务再次做严格 CAS 检查。

审核前若资源任一拥有的数据变更导致版本变化，返回明确冲突并保留待审提议。
**修订后接受只修订提议内容，不用于绕过旧版本冲突。** 本阶段不做自动合并或自动重放；审核者拒绝并解释，作者基于新资料重新提交。
资源隐藏、删除、分类失效或默认语言缺失也不得勉强入库；内部损坏与用户输入错误要区分。

## 审核如何操作

队列按提交时间排序，可按待审核/已处理、类型筛选；不做抢单、分派、批量接受或多人协同草稿。
详情展示当前正式资料、用户原稿、最终采纳预览；提交时基准可展开，冲突时明确指出当前内容已变化。
修订只保存在当前表单中，最后接受时一次提交；不自动保存、不乐观更新、不自动重试。

| 操作 | 行为 |
| --- | --- |
| 原样接受 | 对完整提议校验后应用，不逐字段选择接受 |
| 修订后接受 | 可调整本次允许的知识字段；保存原稿、最终内容和必填修订原因（最多 2,000 字符），页面明确标出审核者改动 |
| 拒绝 | 必填作者可见的安全说明，最多 2,000 字符；不改变正式资源 |
| 内部备注 | 可选，最多 2,000 字符，只有有权审核人员可见；不能混进作者可见说明 |
| 撤回 | 作者只能撤回待审提议；撤回后修订以新提议提交 |

审核修订不能更换目标资源或提议类型，不能修改用户署名/原稿，也不能顺带执行发布、版权或删除等治理操作。
修改后若最终内容与当前资源完全一致，提示无需变更并拒绝本次接受，避免把纯空操作记为成功贡献。
审核者不能接受或拒绝自己的提议；本人可以撤回，或使用现有直接 curation 编辑入口。

### 状态与并发

```text
pending → accepted
        → rejected
        → withdrawn
```

终态不改回待审；冲突不是新的持久化状态。一次提议至多产生一次审核决定和一次正式落库。
接受、拒绝、撤回竞争时按数据库事务决定唯一胜者，其他操作得到明确冲突并重新读取状态，不能静默覆盖。
新资源的 slug 冲突也保持待审，审核者可修改 slug 后再明确提交。

## 作者看见什么

作者可以查看自己的原稿、提交时间、处理状态及安全的结果说明。资源公开时才提供可访问的结果链接。
新资源接受但尚未公开时显示“已采纳，资源尚未公开”，不暴露内部草稿详情或原始 publication_state。
审核后修订内容可在结果允许公开时对比；若资源隐藏/删除，不通过历史接口泄漏当前内容、内部备注、版权状态或隐藏关系。
作者原本提交的内容可以保留为本人记录，服务端基准和审核新增内容不能借此无限公开。

未登录访问私有接口返回认证错误；登录用户猜测他人提议 ID 返回统一未找到。
所有本人记录、编辑上下文、审核接口使用 no-store，页面 noindex。Auth/邮箱/OAuth 信息、会话和内部治理信息不进入贡献 DTO。

## 基础额度与重复请求

建议首版统一采用：**滚动 24 小时最多 10 次提交、同时最多 5 条待审、两次新提交至少间隔 60 秒**。
额度按账号计算，新建与修改共用；拒绝/撤回不返还 24 小时次数，但终态释放待审名额。
已验证的普通账号与后台人员使用公共提交入口时遵守同一规则；后台直接 curation 不计入贡献额度。
1.3 再接入信任与治理策略，本次不建可编程策略系统。

在锁定提交者 User 后，以 PostgreSQL 数据库时间和已有提交记录检查额度，保证并发提交不会超额。
限额返回 429 和可理解的原因/等待信息，客户端保留表单。Redis 故障或清空不能重置业务额度，不新增贡献 Redis key。

每次逻辑提交由客户端生成 request_id，数据库按作者和 request_id 保证唯一，并保存规范化请求指纹。
相同请求重放返回原提议，不重复计额；同键不同内容返回冲突。先验证账号，再查重放，再做新提交额度检查。
网络超时后显式重试必须复用该 ID，修改表单重新提交才换 ID；不把页面刷新或自动重试变成重复贡献。

## 页面与接口边界

| 页面 | 内容 |
| --- | --- |
| Public `/submit` | 新资源表单；带目标 slug 时进入基础修改表单 |
| Public `/me/contributions` | 本人列表、筛选及待审名额提示 |
| Public `/contributions/[id]` | 本人原稿、处理结果与撤回/重新提交入口 |
| Admin `/contributions` | 审核队列，仅 Editorial 可进入 |
| Admin `/contributions/[id]` | 差异、修订预览、接受和拒绝 |

Public 私有表单使用现有 Astro 外壳与 React 交互边界，由浏览器经同源 API 发送会话/CSRF。
匿名 `/resources` 和详情继续纯 SSR，只增加普通贡献链接，不在其中加入个人会话、React island 或服务端凭据转发。
新表单沿用 textarea；差异以转义文本展示，不新增 set:html、富文本编辑器或 HTML sink。

OpenAPI 拟新增以下操作，实际合约冻结时保持一套 generated URL builders：

| 边界 | 操作 |
| --- | --- |
| Public | GET `/contributions/context/{slug}`；POST `/contributions`；GET `/me/contributions`；GET `/me/contributions/{id}`；POST `/me/contributions/{id}/withdraw` |
| Admin | GET `/contributions`；GET `/contributions/{id}`；POST `/contributions/{id}/accept`；POST `/contributions/{id}/reject` |

列表采用既有有界分页，默认 20、最大 100，不提供无限列表。接受请求只发送最终内容、必要的当前基准和说明，不回传重复的整份原稿/基准。
所有写接口保留 Origin/CSRF 和事务内身份校验。贡献 decoder 单独设有界 JSON 限制，约 256 KiB；文本仍按 Unicode 字符计数。
Public/Admin Fiber 总 BodyLimit 须容纳贡献请求，现有 Auth decoder 的 8 KiB 限制保持不变。

## 数据模型建议

只为这两种提议新增迁移；不预建完整 1.2/1.3。使用普通关系表和明确字段，不用 JSONB/EAV 存万能变更。

| 数据 | 保存内容与约束 |
| --- | --- |
| 提议主记录 | 作者、类型、目标、内部基准版本、状态、理由、关联旧提议、request_id/指纹、时间与结果资源引用；作者/类型/原稿不能被审核改写 |
| 类型化资源内容 | 基准、用户原稿、最终采纳三个有限版本；用明确列保存本阶段的资源字段，不是任意键值属性；接受前无最终采纳记录 |
| 初始来源内容 | 仅新资源使用，归属相应内容版本，最多一条，具有明确 URL/type/label/availability 字段；不增加通用来源编辑 |
| 贡献历史 | 提交、接受、拒绝、撤回的操作者、时间、作者可见说明及受限内部备注；修订指向原稿和最终内容，不存任意请求体 |
| 最小业务审计 | 记录审核决定与正式变更的对象、操作者、动作、前后版本/必要引用；同事务提交，不混入 Auth SecurityEvent；1.3 才扩展治理查询 |

明确的外键、唯一约束和 CHECK 防止同一内容版本重复、非法状态和重复 request_id；复杂跨表生命周期由应用事务保障。
类别与规范化规则在提交和接受时都校验；已有退休分类不变时按现有规则保留，新绑定必须有效。
新资源、默认语言和初始来源一同创建，初始 version=1；编辑一次接受只 bump 一次。
SQL、完整列级 DML 矩阵和结构化错误码在编码前随 OpenAPI/迁移冻结，不在讨论阶段添加空包或生成文件。

## 事务与权限设计

公共提交/撤回：锁当前 User → 在同一事务重验账号/会话，提交还要求邮箱已验证 → 查幂等/额度或锁本人提议 → 写记录/历史 → 提交。
提交读取正式资源仍使用 API 的 SELECT 权限和一致快照。撤回不计提交额度；邮箱未验证也可在有效账号会话下撤回本人旧提议。

审核：锁审核者 User → 重验 Admin session/Editorial → 锁提议 → 验证非本人、待审和目标 → 锁正式资源并检查基准 → 校验最终内容 → 写资源/采纳内容/历史/审计 → 提交。
任何一步失败全部回滚，不能分别提交贡献状态和资源变更；不得先调用会独立提交的现有 curation 方法。
在 curation 内复用受控的事务操作，保留原有公开方法的行为，新增协作入口不允许传入伪造的“已授权”标志绕过 Auth。
不通过 Public→Admin HTTP 调用完成写入，不给 Public 进程装配 Admin 连接池，不把事务责任放到 Fiber handler。

| 数据库角色 | 本次变化 |
| --- | --- |
| gfp_api | 正式 Resource Core 仍 SELECT-only；只获得提交、读取本人记录、撤回等用例必需的新表/列权限，由查询强制限定归属 |
| gfp_admin | 新提议/历史/审计所需最小 DML，Resource Core 沿用现有列级写权限；无角色管理或 Auth 扩权 |
| gfp_worker | 不获得贡献或 Resource 权限，无本阶段业务 Job |
| gfp_readonly | 新业务数据只读；运营访问与隐私约束保持现有边界 |

新增迁移从当前版本 6 之后追加，编号在实施开始时重新核对。00001～00006 不变，不修改 gfp_*、gfp:、私密配置或集群权限。
跨角色撤销、会话失效、同一资源竞争及撤回竞争的锁顺序必须在实现时验证，不能以扩大权限或自动重试掩盖问题。

## 验收重点与实施边界

1. 新资源提议可从 UI 提交、审核修订、形成草稿并通过既有流程发布；基础修改可从 UI 提交并准确更新公开资源。
2. 用户原稿不变，修订原因、最终采纳内容、版本和审计记录一致；被拒绝/撤回不会改变正式资源。
3. 未登录、未验证提交、自审、他人提议、Moderator 写入、Origin/CSRF 失败与角色/会话撤销被正确拒绝。
4. 严格旧版本冲突、默认语言变化、退休分类、slug 冲突、非法 URL、超长 Unicode、空修改与隐藏目标处理正确。
5. 并发额度、同键重放/异体、两个审核者、接受/撤回竞争与故障回滚保证唯一结果；没有半成功或多次版本增加。
6. 私有页面不缓存，原稿/最终稿差异不执行 HTML，隐藏资源与内部字段不经贡献 DTO 泄漏，已有 SSR 和 Auth 行为不回归。
7. 在一次性数据库验证新迁移、精确授权和适用的回滚/重放；共享开发只 up，smoke 仅清理自己的夹具。

实现完成运行 `pnpm generate`、`pnpm check`、`pnpm integration:ci`、`pnpm build:images`，再生成并检查 drift。
适用的 `pnpm migrate:dev` 与扩展 `pnpm smoke:admin:dev` 覆盖真实角色的提交/审核流程，复用受保护的私有启动方式，不为每类提议创建独立命令。
最后检查完整 diff、迁移 1～6、最小 grants、秘密与依赖，记录真实验证结果后在 `dev` 本地提交；不 push 或部署。

本轮只形成上述设计与产品决策。进入编码时将讨论稿确认成实施规格，一次交付完整 1.1，不再拆为单独的表/接口/页面任务。
